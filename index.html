01LLM 업무 도구Claude API

검수 메모 정리 도구

날것의 검수 메모를 넣으면 치명도 순으로 이슈를 정리하고, 리뷰 로그 항목을 채우고, 개발자에게 보낼 반려 사유 초안까지 씁니다.

도구 써 보기 → 코드 보기

문제

하루 20개 넘는 게임을 검수하면 판단보다 정리에 시간이 더 듭니다. 플레이하면서 적은 메모를 리뷰 로그의 정해진 항목(크래시, 진행불가, 광고 보상, 저장 등)에 옮기고, 반려할 게임은 사유를 다시 문장으로 씁니다. 같은 내용을 세 번 쓰는 셈입니다.

더 큰 문제는 순서였습니다. 메모는 발견한 순서대로 쌓이는데, 판정은 치명적인 것부터 봐야 합니다. 서버·저장·광고 보상 문제 하나가 오타 열 개보다 무겁습니다.

만든 것

입력플레이하며 적은 메모 그대로
정리치명·주요·경미로 분류, 메모 원문을 근거로 인용
출력판정, 리뷰 로그 항목, 반려 사유 초안, 빠진 확인 항목

설계에서 정한 것

  • 메모에 없는 건 채우지 않는다. 광고를 안 봤으면 "정상지급"이 아니라 "확인불가"로 둡니다. 검수 기록이 틀리는 것보다 비어 있는 게 낫기 때문입니다. 대신 "확인하지 않은 항목"을 따로 뽑아 다음에 볼 것으로 돌려줍니다.
  • 근거는 메모 원문에서만. 이슈마다 메모의 해당 문장을 인용하게 해서, 모델이 만든 문제인지 내가 본 문제인지 바로 구분됩니다.
  • 치명도 기준은 내 판단을 그대로. 실제 검수에서 먼저 보는 순서(서버·저장 → 광고·결제 → 진행불가·크래시 → UI → 텍스트)를 규칙으로 넣었습니다.
  • 출력은 스키마로 고정. 리뷰 로그 DB의 선택지와 같은 값만 나오게 해서, 결과를 그대로 옮겨 붙일 수 있습니다.

써 보니

[실제 업무 메모(비식별화)로 N건 돌려 본 결과를 채울 자리: 정리 시간 전→후, 모델이 틀린 경우와 고친 규칙]

다음에 할 것

  • 판정을 사람이 고친 기록을 모아, 모델과 내 판정이 갈린 비율을 지표로 봅니다.
  • 리뷰 로그 DB에 바로 쓰기. 지금은 복사해서 붙입니다.
02게임 5개 출시Claude Code

3개월, 게임 5개. 매번 AI와 일하는 방식을 고쳤습니다

2026년 7~9월 Verse8에서 게임 5개를 기획·제작·출시했습니다. 한 프로젝트에서 막힌 지점을 다음 프로젝트의 작업 방식으로 바꿔 나갔습니다.

러브버그7월 ~ 8월 중순

서울 땅따먹기. 렉의 원인을 끝까지 찾고, 멀티를 접어 봇전으로 출시. 자세히 ↓

→ 만들기 전에 플랫폼 제약부터 확인한다

어쩌다 인생열흘

배우 IP 홍보용 영상 게임. "숏폼 홍보용"이라는 목적을 먼저 정하고 모든 판단을 거기에 맞춤. 팀 피드백("전개가 너무 빠르다")에 전환 나레이션 3곳으로 답하고, 추가 요청은 비용을 따져 필요한 만큼만 반영. 배포에서 빠진 영상 35개를 약 1/6 용량으로 줄여 올림.

→ 목적 한 줄이 판단 기준이 된다

에이리언 퍼즐팡7월 ~ 9월

퍼즐 게임 롱캣을 오마주하고 아이디어를 덧붙인 500레벨 슬라이딩 퍼즐, 4개 국어. 처음 플레이하며 "되돌리기 없음, 이동 수가 안 보임, 피드백 없음" 등 문제 5개를 짚고 대부분 해결. 별 → 코인 → 꾸미기로 이어지는 반복 동기를 만들고, 새로 얻은 별만 코인으로 쳐서 같은 판 반복 파밍을 막음.

→ AI가 못 하는 단계(이미지 배경 지우기)는 Claude Code로 도구를 직접 만들어 해결한다

색칠공부8월

원스토어 픽셀 색칠 게임. 직접 환불해 보고 기기를 바꿔 가며 확인하다가, 환불 후 상점이 다시 안 뜨는 문제와 광고로 연 그림이 다른 기기에서 다시 잠기는 문제를 찾음.

→ 결제·저장은 "됐다"는 말 대신 서버에서 다시 읽어 확인한다

수상한 펭귄 목장8월 ~ 9월

진짜 펭귄은 돌보고 가짜는 쫓아내는 판별 액션. 색칠공부에서 쓰던 서버 저장 방식을 펭귄에도 맞추고, 화면 크기에 맞춰 늘어나는 레이아웃으로 시작했다가 창마다 손보는 일이 끝없이 이어지자 한 가지 고정 크기로 바꾸자고 제안해 전환.

→ 무대 크기는 첫 주에 하나로 정하고, 에이전트에게는 본 것만 짧게 말한다

03사례 깊이 보기Claude Code

러브버그: 서울 땅따먹기 게임

러브버그 진영과 방역팀 진영이 서울 지도를 나눠 칠하는 5분 라운드제 게임. 제 첫 작품입니다. 멀티플레이로 기획했지만 플랫폼 제약을 확인한 뒤 봇전으로 범위를 줄여 출시했습니다. Verse8 위에서 Claude Code로 기획·구현·수정했습니다.

① 버그 보고를 다시 정의하기

땅을 그리다 꼬리가 안 닫히는 "점령 꼬리 버그"를 조사했습니다. 코드를 확인해 보니 멈춤이나 데드락은 없었습니다.

꼬리 판정 버그
→
돌아갈 우리 땅이 화면에 안 보인다

진짜 문제는 코드가 아니라 정보였습니다. 해결책으로 "내 땅/아군 땅/적 땅" 3색 구분이 제안됐지만, 색이 하나 늘면 작은 화면과 미니맵에서 진영 구분이 흐려집니다. 대신 나침반 화살표 하나를 넣었습니다. 땅을 그리는 중이고 우리 땅이 화면 밖에 있을 때만 나타나, 가장 가까운 아군 땅을 가리킵니다.

② 렉의 진짜 원인을 찾고, 범위를 줄여 출시하기

멀티플레이에서 렉이 계속됐습니다. 첫 가설은 데이터 크기였고, 게임 규칙은 그대로 두고 매 틱 주고받는 데이터를 크게 줄였습니다. 그런데 렉은 그대로였습니다.

렉이 나는 상황을 하나씩 적고, 플랫폼 가이드를 읽으며 AI와 함께 원인을 추적했습니다. 그러다 호출 횟수 제한을 찾았습니다. 같은 함수를 짧은 시간에 너무 자주 부르면 호출 자체가 거부되는 제한이었습니다. 느린 게 아니라 거절당하고 있었던 것입니다.

전송량을 더 줄인다
→
멀티를 접고 봇전으로 출시한다

매 틱 전체 상태를 주고받는 구조 자체가 이 플랫폼과 맞지 않았고, 기획한 규모(한 방에 수십 명)에서는 렉을 피할 수 없었습니다. 플랫폼 운영팀에 직접 문의해 서버 실행 구조를 확인해 보니, 근본적으로 고치려면 게임별 승인이 필요하고 서버 장애 시 복구가 안 되는 단점이 있는 방식으로 바꿔야 했습니다. 그래서 통신 구조를 새로 짜는 대신 멀티플레이를 빼고 봇과 싸우는 게임으로 범위를 줄이자고 제안했고, 그대로 출시까지 끝냈습니다. 진단 과정은 다른 제작자도 같은 함정에 빠지지 않도록 팀 문서로 정리했습니다.

③ 봇이 곧 게임이 되었으니, 봇을 지켜보며 고치기

  • 봇이 땅을 그리다 돌아갈 자리를 잃음 → "나온 자리" 대신 "가장 가까운 아군 땅"으로 돌아가도록 우선순위를 바꿈
  • 봇이 적군에게 반응하지 않음 → 자기보호 규칙을 넣되, 목적 없이 맴도는 봇을 먼저 고쳐야 효과가 제대로 보인다고 보고 순서를 조정
  • 강남을 한강·다리 3개 너머 "보물섬"으로 설계 → 지켜보니 아무도 건너가지 않아 미끼가 안 통한다고 판단, 보통 땅으로 전환. 보상 아이템은 랜덤 구역에 뿌리고 배너로 알림

④ 덜어내기

  • "킬했습니다" 팝업 삭제 → 얻은 점수를 크게 보여줌
  • 협공 토스트, 킬 경보 오버레이, 반복 공지 삭제
  • 겹치던 배너 두 개를 실측해 한 자리에 하나만 뜨도록 구조 자체를 바꿈

일하는 방식

  1. 보고된 문제를 그대로 믿지 않는다. "버그"가 사실은 정보 부족인지, "렉"이 사실은 거절인지 먼저 확인합니다.
  2. 고칠 수 없으면 범위를 줄여서라도 낸다. 러브버그는 멀티를 접고 봇전으로 출시했습니다.
  3. 기획서보다 돌아가는 것을 먼저. 검수 도구도, 게임 5개도 설명보다 결과물이 먼저 있었습니다.
  4. 안 통하면 버린다. 공들인 설계도 실제로 안 통하면 걷어냅니다. 강남 보물섬처럼요.
